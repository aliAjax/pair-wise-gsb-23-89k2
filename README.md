# hxwl-09 半导体洁净室门禁联动

人员组 · 房间 · 物料 · 灭菌批次 · 压差规则 · 通行许可 全链路联动演示。

## 技术栈

React + Vite + TypeScript + CSS（无后端，状态全部在内存，`src/store.ts` 为单一规则引擎）

## 本地运行

```bash
npm install
npm run dev       # 端口 5109
npm test          # 50 项端到端规则场景（过期/压差/互锁/离线回传/冲突裁决/批次重试）
npm run build     # tsc 类型检查 + 生产构建
```

## 已接起来的领域规则

1. **通行许可**：签发时冻结压差规则版本与灭菌批次版本，把「人员组 → 房间 → 物料 → 批次」绑定到许可编号。
2. **外门统一判定**（`src/domain.ts:checkOuter`）：许可状态 → 物料灭菌有效期 → 房间压差 → 通道异常 → 互锁占用。
   - 物料过期、压差不合格、许可失效/冲突：**停在外门**，写明具体原因（物料/批次/有效期、实际压差与阈值）。
   - 通道满载（同刻已有一组）或异常未结：进入**待处理队列**，FIFO 放行；队列项的阻挡原因与审计记录**同一句文案、同一原因码**。
3. **互锁通道**：同一通道同时只允许一组；占用期间其余许可排队；离场释放后队列才能推进。许可进入房间即核销，**已进入的通行不能再次开门**（在线/离线重复刷卡都驳回）。
4. **规则调整即失效**：压差规则或灭菌批次有效期调整后，关联的已签发许可立即变「失效待确认」，按最新规则重新确认通过前不能进入；批次提前到已过期时，重新确认同样拦截。
5. **断网门控**：断网瞬间生成本地缓存快照，门控按快照判定并把每个门动作（外门/进互锁/进房间/重复刷卡）登记为待回传事件。
6. **回传合并**：恢复后按批次（每批 3 条）回传，**按许可编号归并**；中心再按最新数据复核——门控本地已硬阻挡的不会被中心补开门。
7. **同字段冲突**：断网期间门控与中心改了同一字段（演示字段：随行备注）且取值不同 → 两版都保留，许可挂「冲突待裁决」，整组门事件暂扣，**等班长裁决**：采用门控版则按事件顺序补执行；采用中心版则离线门动作驳回、许可转重新确认。
8. **失败批次重试**：可勾选模拟某批回传失败；重试只发失败批次里未完成的门（按门动作发生顺序），已 acked / 已进入的不会重发或重复开门，下一批未失败的事件不被卷入。
9. **同源阻挡原因**：原因码 + 文案只从 `reasonText()` 一处产出，操作页横幅、待处理队列卡片、追溯审计记录展示完全一致。

## 页面

- **门禁操作页**：刷卡开外门、互锁/内门推进、离场、通道异常登记与关闭、实时压差。
- **许可 / 物料 / 规则**：签发许可、规则版本调整、灭菌批次有效期调整、失效许可重新确认。
- **离线门控与回传**：断网/恢复、门控本地面板、双方同字段修改、失败模拟、批次回传、班长裁决、事件流水。
- **待处理队列**：满载/异常队列项、FIFO 放行、原因随最新状态更新。
- **追溯记录**：全部门动作、拦截、失效、合并、裁决的不可变审计流（新记录在前）。
